# POORCRAFT 3D Task Contract

## Identity

- Task ID: P3D-001
- Title: Separate workspace, executable identity, and no-accidental-save-sharing guard
- Stage/gate: P3D-000 (project boundary and truth)
- Owner/model: owner directive "make all in the README"; z.ai GLM session
- Date: 2026-09-03

## Goal

POORCRAFT 3D exists as its own Rust workspace with its own executable name
and save location, such that running or saving the new game can never touch
the original POORCRAFT/LOREFORGE saves, and the test suite rejects any code
path that would blur the two identities.

## Current truth

- Repository: single Cargo workspace at the root (members: `crates/lf_*`,
  `apps/*`, `xtask`); the original game's saves live in `worlds/`
  (`ClientSave`, `identity.dat`) and the original binaries are
  `loreforge` / `loreforge-server`.
- `docs/POORCRAFT-3D/` exists as an approved design pack; no P3D code exists.
- Root workspace membership is an explicit list, so a nested workspace under
  `poorcraft3d/` is naturally independent.

## Scope

### Must change

- New nested Cargo workspace `poorcraft3d/` with its own target dir, crate
  `pc3d_core`, and binary `poorcraft3d`.
- `pc3d_core::identity`: project identity constants (name, executable name,
  save root, save-file magic `PC3D`, format epoch) and
  `refuse_foreign_save()` which rejects any file not carrying the P3D magic.
- Guard tests: P3D save root/executable must differ from the original
  game's (`worlds`, `loreforge`); a POORCRAFT-style save file (LOREFORGE
  magic) is refused; a P3D magic file is accepted; the guard is case-strict.
- Makefile targets `p3d-build` / `p3d-test`; `.gitignore` entry for
  `poorcraft3d/target`.
- `cargo test --workspace` at the ROOT stays green and untouched; the P3D
  workspace carries its own suite.

### Explicit non-goals

- No versioned headers/refusal behavior matrix (P3D-002).
- No deterministic clock/commands/journal (P3D-003), no profiler (P3D-004),
  no empty-world runtime or window (P3D-005).
- No reuse of lf_* crates by path dependency; ideas only, checked contracts.
- No compatibility or importer for POORCRAFT saves (D-002).

## Contracts and invariants

- deterministic behavior: identity constants are `const`; guard decisions are
  pure functions of (bytes, constants) — no IO in the decision path.
- authority/ownership: `pc3d_core` owns the project identity; no other crate
  may redefine the save root or magic.
- save/load behavior: P3D saves live under `saves3d/`; any file whose header
  magic is not `PC3D` is refused before parsing (refusal tested with a
  fabricated LOREFORGE-style file).
- network behavior: none in this task.
- performance budget: none (no runtime loop yet).
- player-visible result: `poorcraft3d --identity` prints the project
  identity block and exits 0 — the new game answers "who am I" without
  touching the old one.

## Verification

- unit/integration tests: pc3d_core suite (identity invariants, guard
  accept/refuse, path-separation invariants); root workspace suite unchanged
  and green.
- persistence/replay tests: n/a (P3D-002+).
- visual proof scene: n/a (no renderer yet; P3D-005 first).
- smoke or multiplayer test: `poorcraft3d --identity` exits 0 (run manually
  and recorded in DEVLOG until P3D-005 adds the headless smoke path).
- profiling/counter evidence: n/a.

## Done when

pc3d_core tests + root workspace tests are green, the binary answers
`--identity`, the guard demonstrably refuses a LOREFORGE-magic file, and
STATE/DEVLOG/CHANGELOG/Makefile agree.

## Handoff

- files changed: `poorcraft3d/*` (new), `Makefile`, `.gitignore`, `STATE.md`,
  `CHANGELOG.md`, `DEVLOG.md`
- commands run: `cargo test` (both workspaces), `./target/release/poorcraft3d --identity`
- evidence paths: this contract, DEVLOG entry
- known limitations: the binary is a stub; nothing renders or saves yet.
- next task: P3D-002 (version headers + refusal behavior).

## Required design check

- Which player story does this improve? None directly — it is the boundary
  that lets every future story exist without corrupting either game.
- Which two game layers does it connect? Repository/process boundary ↔
  future persistence layer (the save root and magic P3D-002 will format).
- What must a player be able to see or do when it works? Launch
  `poorcraft3d` and see the new game identify itself; POORCRAFT saves stay
  untouched in `worlds/`.
- What user-approved decision does it depend on? D-001 (separate project,
  separate identity/workspace) and D-002 (brand-new format, no implicit
  compatibility); language Rust per D-013.
